# eggwork-core

`eggwork-core` owns the protocol-neutral, bounded domain vocabulary that every other crate in the workspace agrees on: identity newtypes, the execution request shape, resource/isolation/network requirements, the workspace manifest and patch models, the outcome and event types, node capability and status facts, every protocol limit constant, the validation error vocabulary, and the two canonical request-digest functions. It is a single 1,671-line file (`crates/eggwork-core/src/lib.rs`) with `#![forbid(unsafe_code)]` at the top and no workspace-internal dependencies at all. What it deliberately does not know about is everything outside the domain: wire format, transport, scheduling, and process mechanics. It describes *what* an execution is, never *how* it is framed on the wire, routed, placed, or run.

Source references in this document are repo-root relative and use `crates/eggwork-core/src/lib.rs:LINE` form.

## Responsibility boundary

Owns:

- Every hard protocol bound as a `pub const` (`lib.rs:10-29`): identifier size, argv/env counts and sizes, stream and capture sizes, metadata and capability counts, and the four workspace tree bounds.
- Nominal identity newtypes generated by one macro: `NodeId`, `PrincipalId`, `ExecutionId`, `LeaseId`, `WorkspaceId`, `ArtifactId` (`lib.rs:49-107`).
- Ordering primitives with different semantics: `ExecutionGeneration` (ownership epoch) and `EventSequence` (observation order), plus `BlobDigest` as the content address.
- The request model: `CommandSpec`, `ExecutionSpec`, `ExecuteRequest`, and the resource/isolation/network requirement types.
- The portable workspace model: `WorkspaceManifest`, `WorkspaceEntry`, `WorkspaceManifestPatch`, `WorkspacePatchEntry`, and the private `validate_portable_workspace_path`.
- The outcome and event model: `ExecutionState`, `ExecutionRejection`, `ExecutionFailure`, `SandboxResult`, `ResourceResult`, `ExecutionFinalizationFailure`, `ExecutionResult`, `ArtifactRecord`, `ExecutionEvent`.
- Node facts: `NodeCapabilities`, `NodeStatus`, `ProtocolVersion`, `ProtocolVersionRange`.
- The canonicalization contract: `CANONICAL_REQUEST_VERSION`, `CANONICAL_WORKSPACE_REQUEST_VERSION`, `request_digest`, `request_digest_with_workspace`, `WorkspaceManifest::digest`.
- Two error shapes that other crates consume: `ValidationError` and `ApiError`.
- Secret-hygiene behavior in `Debug` for command argv, environment values, stdin, event payloads, event metadata, and `ExecutionHandle::lease_id`.

Refuses to know:

- **Wire format.** No JSON-RPC/HTTP/transport shapes, no operation names, no status-code mapping, no framing. `ApiError` is a bare `{schema_version, code, message}` with an untyped `String` code; the code vocabulary and its HTTP binding live in `eggwork-server`.
- **Transport.** No sockets, TLS, principal resolution, or session state. `PrincipalId` exists as an opaque newtype with no derivation rules; per `plans/001-terminology-and-domain-model.md` §3, principal identity is transport-derived and must never be accepted from a payload — this crate simply never resolves one.
- **Scheduling and placement.** No node selection, no fairness or priority queue, no retry policy. `NodeStatus.draining` and `NodeStatus.active_executions` are reported facts, not decisions (`plans/001-terminology-and-domain-model.md` §17-18).
- **Process mechanics.** No spawn, no argv-to-exec translation, no cgroups/Landlock, no environment reconstruction, no stream draining, no exit-status interpretation. `CommandSpec` is the declarative input to that machinery, never an implementation of it. Core is also forbidden from creating OS children (see [Dependencies](#dependencies)).
- **Storage.** No blob store, no materializer, no journal, no quota accounting. `BlobDigest` is an address, not a retrieval mechanism.
- **Admission policy.** `IsolationRequirement` and `NetworkRequirement` state what is *asked for*; deciding whether a node can honor them is `eggwork-server` local admission.

## Protocol limits

All twenty constants live in one block at `lib.rs:10-29` and are the only numbers a caller needs to pre-flight a request.

### Identifiers

| Constant | Value | What it bounds |
|---|---|---|
| `MAX_ID_BYTES` | `128` | Byte length of every `id_type!` identity. Measured with `String::len()`, so it is UTF-8 bytes — though the charset check makes any accepted id ASCII. |

### Command and environment

| Constant | Value | What it bounds |
|---|---|---|
| `MAX_ARG_COUNT` | `256` | Number of entries in `CommandSpec.argv`. |
| `MAX_ARG_BYTES` | `32768` (32 KiB) | Byte length of a single argv entry. Checked per entry at `lib.rs:498-506`; there is no bound on the *total* argv byte size. |
| `MAX_ENV_COUNT` | `256` | Number of `EnvironmentEntry` values. |
| `MAX_ENV_NAME_BYTES` | `256` | Byte length of one environment variable name. |
| `MAX_ENV_VALUE_BYTES` | `16384` (16 KiB) | Byte length of one environment variable value. |
| `MAX_OUTPUTS` | `128` | Number of `DeclaredOutput` entries. No bound on aggregate declared output size. |

### Streams, capture, and time

| Constant | Value | What it bounds |
|---|---|---|
| `MAX_STDIN_BYTES` | `4194304` (4 MiB) | Length of `StdinPolicy::Bytes` payload. |
| `MAX_EVENT_CHUNK_BYTES` | `65536` (64 KiB) | Payload length of one `ExecutionEvent` (stdout chunk, stderr chunk, or diagnostic string). Per event, not cumulative. |
| `MAX_CAPTURE_BYTES` | `16777216` (16 MiB) | `OutputPolicy::capture_limit_bytes` ceiling — the retained stdout/stderr budget for one execution. |
| `MAX_TIMEOUT` | `Duration::from_secs(604800)` (7 days) | `CommandSpec::timeout_millis` ceiling. |

`MAX_TIMEOUT` is worth pausing on. The field is a plain `u64` of milliseconds, whose natural domain is roughly 5.8e11 years, so without a ceiling a single request could ask for an effectively immortal process. The value is not a claim about what hardware can sustain; it is what makes the field *total*. There is no `Option<u64>` and no sentinel for "no deadline": `CommandSpec::validate` rejects `timeout_millis == 0` alongside the ceiling (`lib.rs:533-535`), so **every accepted spec carries a finite deadline**. That is a precondition for terminal convergence and for any retention or lease accounting downstream. The constant is also cheap to tighten later — a pure validation change, no type or field change. `MAX_TIMEOUT.as_millis()` is `u128` and is cast to `u64`; at 604,800,000 there is no truncation.

### Metadata, capabilities, and paths

| Constant | Value | What it bounds |
|---|---|---|
| `MAX_METADATA_COUNT` | `64` | Pairs in `ExecutionSpec.metadata` and in `EventMetadata::fields` (`lib.rs:566`, `lib.rs:989`). |
| `MAX_METADATA_KEY_BYTES` | `128` | One metadata key. Checked in `ExecutionSpec::validate`; *not* checked in `EventMetadata::validate`. |
| `MAX_METADATA_VALUE_BYTES` | `2048` | One metadata value — and, reused, one `NodeCapabilities.features` entry (`lib.rs:1080`). See [Review focus](#review-focus). |
| `MAX_CAPABILITIES` | `256` | Number of entries in `NodeCapabilities::features`. |
| `MAX_PATH_BYTES` | `4096` | One `RelativePath`, and one raw workspace path inside `validate_portable_workspace_path`. |

### Workspace

| Constant | Value | What it bounds |
|---|---|---|
| `MAX_WORKSPACE_ENTRIES` | `4096` | `WorkspaceManifest.entries`, and `WorkspaceManifestPatch.entries`. |
| `MAX_WORKSPACE_PATH_BYTES` | `1048576` (1 MiB) | **Aggregate** sum of raw path byte lengths across all entries, accumulated with `saturating_add` (`lib.rs:641-646`). The tree-wide defense against many-deeply-nested-path manifests. |
| `MAX_WORKSPACE_DEPTH` | `128` | `path.split('/').count()` — component count, not nesting edges, so the root-relative depth is 128 components. |
| `MAX_WORKSPACE_LOGICAL_BYTES` | `2147483648` (2 GiB, `u64`) | Sum of `File.size_bytes` across the manifest, accumulated with `saturating_add` (`lib.rs:659-666`). |

Three workspace bounds are aggregate and two are per-entry, and they are *not* redundant: 4,096 short paths fit the count but the 1 MiB path-bytes bound; a single 2 GiB file fits the logical bound alone. `MAX_WORKSPACE_DEPTH` is enforced only inside `validate_portable_workspace_path`, so it applies to manifest entries, not to `RelativePath` in general.

## Identity and versioning

### Identity newtypes

Six types come from the `id_type!` macro at `lib.rs:49-100`: `NodeId`, `PrincipalId`, `ExecutionId`, `LeaseId`, `WorkspaceId`, `ArtifactId`. They are six *nominal* types with identical internals — a `NodeId` cannot be passed where an `ExecutionId` is expected, so no downstream crate can accidentally substitute identities. Each wraps a private `String` and exposes `new`, `as_str`, `TryFrom<String>`, `From<T> for String`, `Display`, and a `Debug` that renders as a tuple of the type name and inner value.

The shared invariant is enforced only in `new` (`lib.rs:55-73`): non-empty, at most `MAX_ID_BYTES`, and every byte is ASCII alphanumeric or one of `-`, `_`, `.`, `:`. Anything else is `ValidationError::InvalidSyntax`. Because the inner field is private, the only ways to obtain one are `new`, `TryFrom<String>`, or `Deserialize` — and deserialization is routed through `#[serde(try_from = "String")]`, so the same validation runs on the wire path. There is no `Copy` (it wraps a `String`), but `Ord` and `Hash` are derived, so ids are usable as map keys and set members.

Two consequences worth stating precisely: `:` is in the charset, so ids can be namespaced (`node:1`) without a separate namespace field; and there is no case folding, so `NodeA` and `nodea` are distinct identities. `Debug` on any bare id prints the raw value unredacted — redaction is applied at the *container* level, e.g. `ExecutionHandle` hides `lease_id` (`lib.rs:1133-1141`).

### Ownership order vs observation order

`ExecutionGeneration` (`lib.rs:109-125`) and `EventSequence` (`lib.rs:127-137`) are both `#[serde(transparent)]` wrappers over `u64` with derived `PartialOrd`/`Ord`/`Hash`, and they mean different things on purpose:

- `ExecutionGeneration` is the ownership epoch for one `ExecutionId` (`plans/001-terminology-and-domain-model.md` §5). It is a fencing primitive, not a retry count. `new` rejects `0` with `OutOfRange`, so the first epoch is `1` and there is no "generation zero" to confuse with a default-initialized value. It appears on `ExecutionSnapshot`, `ExecutionHandle`, and `ArtifactRecord`.
- `EventSequence` orders observations within a stream (`plans/001-terminology-and-domain-model.md` §14). Its `new` is a `const fn` that accepts any `u64` including `0` — no bound at all. It appears only on `ExecutionEvent`.

The two are deliberately not unified: an event stream is generation-scoped (ADR-0003 §15) so a stale stream cannot be mistaken for a newer epoch, but the *numbering spaces are independent*. Note that `ExecutionEvent` carries no `ExecutionGeneration` and no `ExecutionId` — the generation scoping has to come from whatever envelope carries the stream, which is outside this crate.

### Content addresses

`BlobDigest` (`lib.rs:139-173`) is a `String` with `#[serde(try_from = "String", into = "String")]`. Two directions:

- `from_bytes` computes `hex::encode(Sha256::digest(bytes))` — construction always produces a valid digest.
- `parse` enforces exactly 64 bytes, all ASCII hex digits, none of them uppercase, and otherwise returns `ValidationError::InvalidSyntax { field: "sha256 blob digest" }`.

The lowercase-only rule is the load-bearing part: it gives a content address **exactly one textual representation**, so two callers cannot produce different strings for the same bytes. That is what makes a digest usable as a map key, as `base_manifest_digest` on a patch, and as the identity a caller echoes back. `hex::encode` is what fixes the case, and `parse` refuses the alternative. `BlobDigest` derives `PartialEq`/`Eq`/`Hash` but notably **not** `Ord` — nothing in the crate sorts or ranges over digests.

### Versions and envelopes

`ProtocolVersion { major: u16, minor: u16 }` is a `Copy` data pair with derived ordering, major first; `ProtocolVersionRange { min, max }` is a plain pair with no validation of its own and no `Copy`. The only check that `min <= max` lives in `NodeCapabilities::validate` (`lib.rs:1068-1072`), not on the range.

`Versioned<T> { schema_version: u16, value: T }` (`lib.rs:1097-1101`) is a generic versioned envelope. It is **declared and never used** — no type in the crate has a `Versioned` field, and no code in the crate constructs one. The crate's actual convention is a duplicated explicit field: `ExecuteRequest`, `ExecutionAccepted`, `ExecutionSnapshot`, and `ApiError` each carry `schema_version: u16` directly, and `ExecutionSpec` carries a *second*, independent one. A reviewer should decide whether `Versioned<T>` is a reserved generic form or dead surface.

Three different version axes coexist here, with three different openness rules — this is a real source of confusion:

| Axis | Field | Accepted values |
|---|---|---|
| Envelope/wire schema | `schema_version` on request/response structs | any non-zero `u16` (`ExecutionSpec::validate` rejects `0`) |
| Workspace tree schema | `schema_version` on `WorkspaceManifest` and `WorkspaceManifestPatch` | exactly `1` (`lib.rs:623-627`, `lib.rs:757-761`) |
| Canonicalization algorithm | `CANONICAL_REQUEST_VERSION`, `CANONICAL_WORKSPACE_REQUEST_VERSION` | fixed by the digest functions |

## Request model

The model is a four-step nest, then three response shapes.

### `CommandSpec` — what to run

`lib.rs:458-541`. Ten public fields: `argv`, `cwd: Option<RelativePath>`, `environment: Vec<EnvironmentEntry>`, `stdin: StdinPolicy`, `timeout_millis: u64`, `output: OutputPolicy`, `declared_outputs: Vec<DeclaredOutput>`, `resources: ResourceRequirements`, `isolation: IsolationRequirement`, `network: NetworkRequirement`.

There is no shell string. `argv` is the executable plus arguments, matching `plans/001-terminology-and-domain-model.md` §9 (an explicit shell mode would be a separate requested capability, and no such field exists). `cwd` is an *optional relative path within the workspace* — a node-local locator, not workspace identity, which is why it is a `RelativePath` and not a `WorkspaceId`.

`CommandSpec::validate` (`lib.rs:488-540`) runs in a fixed order and delegates outward:

1. `argv` non-empty, at most `MAX_ARG_COUNT`, each entry at most `MAX_ARG_BYTES` and free of NUL.
2. `environment` at most `MAX_ENV_COUNT`; **every** entry is re-validated by calling `EnvironmentEntry::new(&e.name, &e.value)` (`lib.rs:513-515`) — re-validation, not a trust of already-constructed entries.
3. `environment` names are unique, via a `HashSet<&str>` (`lib.rs:516-526`).
4. `declared_outputs` at most `MAX_OUTPUTS`.
5. `timeout_millis` in `1..=MAX_TIMEOUT`.
6. `self.stdin.validate()`, `self.output.validate()`, `self.resources.validate()`.

What `validate` does **not** do is as important: it does not check `argv[0]` is non-empty or path-like, does not bound total argv bytes, does not check `declared_outputs` paths for duplicates, and never validates `IsolationRequirement` or `NetworkRequirement` — neither type has a `validate` method at all.

`Debug` for `CommandSpec` is hand-written (`lib.rs:471-486`): `argv` is replaced with `"[REDACTED]"` outright (not just a length), while every other field is printed normally, delegating to the redacting `Debug` impls of `EnvironmentEntry`, `StdinPolicy`, and `ExecutionSpec`'s metadata. The test at `lib.rs:1264` pins this for argv, env, stdin, and metadata secrets.

### `ExecutionSpec` — the execution-defining description

`lib.rs:543-585`. Three fields: `schema_version: u16`, `command: CommandSpec`, `metadata: Vec<(String, String)>`. `validate` runs `command.validate()` first, then requires `schema_version != 0`, then bounds metadata: at most `MAX_METADATA_COUNT` pairs, each key non-empty and at most `MAX_METADATA_KEY_BYTES`, each value at most `MAX_METADATA_VALUE_BYTES`, no NUL in either. Metadata keys have no charset restriction beyond that (unlike environment names), and **duplicate metadata keys are not rejected** — unlike duplicate environment names, which are.

`Debug` prints `metadata_count` and the redacted `command`, never metadata values (`lib.rs:549-557`).

### `ExecuteRequest` and the responses

- `ExecuteRequest { schema_version, spec: ExecutionSpec }` (`lib.rs:1103-1107`) is the submission envelope. It has **no `validate()` method**; the caller must reach into `spec`. The server does exactly that at `crates/eggwork-server/src/lib.rs:1552` (`wire.spec.validate()`) before computing the digest.
- `ExecuteRequest` has no workspace field. Workspace identity enters the domain only through the digest call, `request_digest_with_workspace(&wire.spec, wire.workspace_id.as_ref())` at `crates/eggwork-server/src/lib.rs:1606`; the manifest itself travels separately.
- `ExecutionAccepted { schema_version, execution_id, state }` (`lib.rs:1109-1114`) — admission succeeded, and the state is whatever the node was at acceptance (`Accepted` in practice). A rejection produces no `ExecutionAccepted`.
- `ExecutionSnapshot { schema_version, execution_id, generation, state, result: Option<ExecutionResult> }` (`lib.rs:1116-1123`) — the bounded point-in-time view, per `plans/001-terminology-and-domain-model.md` §15. Presence of `result` is what distinguishes a running snapshot from a terminal one, and the type does not enforce that relationship.
- `ExecutionHandle { execution_id, generation, lease_id }` (`lib.rs:1125-1141`) — the fenced control handle. Its doc comment states the intent: the lease token is bearer authority and is omitted from `Debug`. `Serialize` is derived and unredacted, so the token *is* emitted on the wire by design; only logging is scrubbed.

### The `Requirement<T>` three-state design

`Requirement<T>` (`lib.rs:352-405`) has three variants: `NotRequested`, `BestEffort(T)`, `Required(T)`. It derives `Debug`, `Clone`, `Copy`, `PartialEq`, `Eq` — no `Hash`, no `Ord` — and implements `Default = NotRequested`. Its `Serialize`/`Deserialize` are hand-written, not derived.

Why three states rather than `Option<T>` plus a `strict: bool`: it makes the *relationship between asking and not getting* representable without ambiguity. `Option<T>` cannot distinguish "I don't care" from "give me at least this much, or refuse"; a bare `T` cannot distinguish "hard floor" from "advisory floor". `Requirement` lets a request say `Required(8 GiB)` and a node answer "I cannot enforce that" as a **rejection at admission**, versus `BestEffort(8 GiB)` where the same answer degrades to a recorded outcome instead. The outcome side mirrors it exactly: `ResourceDimensionResult` is `NotRequested` / `NotApplied { reason }` / `Applied { backend }` / `LimitExceeded { backend }`, and `SandboxResult` is `NotRequested` / `NotApplied { reason }` / `Applied { profile }` / `Failed { reason }` (tagged `status`). `IsolationRequirement { None, BestEffort, Required }` and `NetworkRequirement { Unrestricted, Disabled, AllowListed(Vec<String>) }` are the flat, value-free analogues for isolation and network.

The custom serde encoding is deliberately backward-compatible with a legacy shape. Serializing: `NotRequested` → `null`; `BestEffort(v)` → the bare value `v`; `Required(v)` → `{"required": v}`. Deserializing (`lib.rs:384-405`) buffers into a `serde_json::Value` and then: `null` → `NotRequested`; an object of exactly one key named `required` → `Required`; anything else → `BestEffort` via `T::deserialize`. So a bare number keeps meaning "best effort", which is why the test name at `lib.rs:1309` is `resource_requirements_preserve_legacy_best_effort_shape_and_accept_required_values`. Two consequences: an object of one key `required` cannot ever express `BestEffort` (irrelevant for the `u64`/`u32` instantiations actually used), and the deserializer is **JSON-codec-specific** — it cannot work under a non-self-describing format such as bincode or CBOR.

`ResourceRequirements` (`lib.rs:342-350`) holds three `Requirement` fields — `memory_bytes: Requirement<u64>`, `cpu_millis: Requirement<u64>`, `pids: Requirement<u32>` — each `#[serde(default)]`, so a missing key is `NotRequested`. `validate` (`lib.rs:407-435`) accepts `NotRequested` unconditionally and otherwise requires a **non-zero** value within a per-dimension ceiling via range patterns on the enum: memory `1..=1_125_899_906_842_624` (1 PiB), cpu `1..=1_000_000` ms, pids `1..=1_000_000`. Those three ceilings are inline literals, not `pub const` — unlike every other bound in the crate.

### Policies, stdin, declared outputs, and environment

- `StdinPolicy { Null, Bytes(Vec<u8>) }` (`lib.rs:270-299`). `Null` and a bounded byte payload. `validate` checks only the length bound. `Debug` prints `Bytes { length, value: "[REDACTED]" }`.
- `OverflowPolicy { Truncate, Terminate }` (`lib.rs:301-305`) — the declared behavior when output exceeds the capture budget. Two variants, no data, no validation, no rename attribute.
- `OutputPolicy { capture_limit_bytes, event_chunk_bytes, overflow }` (`lib.rs:307-334`) with `Default` = `1 MiB` / `16 KiB` / `Truncate` — note these defaults are *not* expressions of `MAX_CAPTURE_BYTES` / `MAX_EVENT_CHUNK_BYTES`; they are independent literals that happen to be 1/16 and 1/4 of the maxima. `validate` requires `capture_limit_bytes <= MAX_CAPTURE_BYTES`, `event_chunk_bytes` in `1..=MAX_EVENT_CHUNK_BYTES`. It does **not** require `event_chunk_bytes <= capture_limit_bytes`, and it accepts `capture_limit_bytes == 0`.
- `DeclaredOutput { path: RelativePath, required: bool }` (`lib.rs:336-340`) — a declared capture target and whether its absence is a failure. This is the declaration mechanism from ADR-0004 decision 10: Eggwork captures only declared paths, and `ArtifactType` has exactly one variant (`File`) because nothing else is in scope.
- `EnvironmentEntry { name, value }` (`lib.rs:229-268`). `new` requires a name that is non-empty, at most `MAX_ENV_NAME_BYTES`, ASCII alphanumeric or `_` only, **not** starting with an ASCII digit (`is_some_and(u8::is_ascii_digit)` at `lib.rs:248`), and NUL-free; and a value at most `MAX_ENV_VALUE_BYTES` and NUL-free, with a NUL value reported as `Forbidden { field: "environment value NUL" }`. A leading underscore is allowed; a hyphen in a name is not. `Debug` prints the name and `"[REDACTED]"` for the value.
- `RelativePath` (`lib.rs:187-227`) is the single path type and its safety rules are: non-empty, at most `MAX_PATH_BYTES`, not starting with `/`, no `\`, no NUL, and no `/`-delimited component that is empty, `.`, or `..`. The empty-component rule subsumes trailing slashes and doubled slashes. It is **not** ASCII-restricted, has no trailing-dot or trailing-space rule, and no Windows reserved-name rule — those stricter rules exist only in `validate_portable_workspace_path` for workspace trees. The inner `String` is private, so every `RelativePath` in the system has passed these checks; `"C:/secret"` and `"café.txt"` are legal `RelativePath` values that the workspace validator rejects separately (asserted at `lib.rs:1431-1433`).

## Workspace model

### Manifest and entries

`WorkspaceManifest { schema_version: u16, entries: Vec<WorkspaceEntry> }` (`lib.rs:589-593`) carries the doc comment that states the portability contract: *"Portable file-tree description. Version 1 uses conservative ASCII paths and rejects symlinks so materialization stays identical across hosts."*

`WorkspaceEntry` (`lib.rs:595-611`) is an internally tagged enum (`#[serde(tag = "type", rename_all = "snake_case")]`): `Directory { path }`, `File { path, digest: BlobDigest, size_bytes: u64, executable: bool }`, and `Symlink { path, target: String }`. The `Symlink` variant is **always rejected by `validate`**, unconditionally, with `Forbidden { field: "workspace symlink" }` (`lib.rs:667-671`) — it exists in the type so the shape can be expressed and refused, and there is a test for exactly that. `WorkspaceEntry::path()` returns the `RelativePath` for all three variants. The `executable` bit is the only filesystem metadata in scope, matching ADR-0004's "initial metadata scope" (no ownership, ACLs, xattrs, device nodes, sockets, FIFOs).

`WorkspaceManifest::validate` (`lib.rs:622-690`) is the single tree validator, and it runs in a deliberate order:

1. `schema_version != 1` → `OutOfRange { field: "workspace schema version" }`. Closed, not an open range.
2. `entries.len() > MAX_WORKSPACE_ENTRIES` → `TooMany`.
3. Per entry: `validate_portable_workspace_path(raw_path)`; accumulate raw path bytes into `MAX_WORKSPACE_PATH_BYTES`; insert the ASCII-lowercased path into a `HashSet` and reject a **case collision** (`InvalidSyntax { field: "workspace case collision" }`); insert the exact path into a `BTreeMap<&str, bool>` keyed by path and valued by "is a directory", rejecting an exact **duplicate**; for `File`, accumulate `size_bytes` into `MAX_WORKSPACE_LOGICAL_BYTES`; for `Symlink`, reject; for `Directory`, nothing.
4. A second pass over all entries walking every `/` offset, requiring each ancestor prefix to already be present in the map **as a directory** (`paths.get(parent) != Some(&true)` → `InvalidPath { field: "workspace parent directory" }`).

The `BTreeMap<&str, bool>` is what makes file/directory conflicts (`a` as a file *and* `a/b`) fall out of the same parent-closure rule as a missing parent: `a` is in the map with value `false`, the lookup returns `Some(&false)`, and the check fails. The case-collision pass is why the manifest is portable to case-insensitive hosts: `A` and `a` cannot coexist even on a case-sensitive one. Note the parent-closure pass is `O(total path bytes)` in the worst case and is fully deterministic regardless of entry order.

`logical_bytes()` (`lib.rs:692-700`) re-derives the `File` total with `fold(0u64, u64::saturating_add)` — the same arithmetic as the validator, exposed as an accessor for quota/GC callers.

`WorkspaceManifest::digest()` (`lib.rs:702-710`) is the content address for a workspace tree: clone the manifest, `sort_by` entries on `path().as_str()` (Rust's `sort_by` is stable), prefix the serialized bytes with `b"eggwork-workspace-manifest\0canonical-json-v1\0"`, and SHA-256 them. Three things to note. The prefix is its own domain-separation tag with its **own** version (`v1`), independent of the request digest's `v2`/`v3`. The sort is what makes the digest order-independent, so two manifests that list the same tree in different orders have the same address. And `digest()` does **not** call `validate()` first — an unvalidated manifest can be digested.

`validate_portable_workspace_path` (`lib.rs:828-876`) is private, so it is reachable only through `WorkspaceManifest::validate` (and the tests). It rejects, at the whole-path level: empty, over `MAX_PATH_BYTES`, over `MAX_WORKSPACE_DEPTH` components, non-ASCII, leading `/`, `\`, NUL. Per component: empty, `.`, `..`, trailing `.`, trailing space, any byte `< 0x20`, and any of `< > : " | ? *`. It then uppercases the portion before the first `.` and rejects the DOS device set `CON`, `PRN`, `AUX`, `NUL`, `CONIN$`, `CONOUT$`, `CLOCK$`, plus `COM1`–`COM9` and `LPT1`–`LPT9` (note `COM10` is *not* rejected, since the check requires the remainder to be a single digit `1`–`9`). That last block is the only rule reported with a different `field` label: `InvalidPath { field: "reserved workspace path" }`.

### Manifest vs patch

`WorkspaceManifestPatch` and `WorkspacePatchEntry` (`lib.rs:713-753`) exist because re-sending a whole manifest per revision is wasteful for a 2 GiB, 4,096-entry tree. The doc comment states the contract precisely: the patch names its content base by digest and carries exact-path remove/upsert entries; **applying a patch to a base manifest MUST yield the same canonical manifest and digest as submitting the final manifest directly**; and patch ordering never affects the result.

`WorkspaceManifestPatch { schema_version, base_manifest_digest: BlobDigest, entries: Vec<WorkspacePatchEntry> }`. `WorkspacePatchEntry` is internally tagged with the same `type` tag: `Remove { path }`, `Directory { path }`, `File { path, digest, size_bytes, executable }`. There is deliberately **no** `Symlink` patch variant, so a patch structurally cannot introduce one.

`WorkspaceManifestPatch::validate` (`lib.rs:756-777`) checks only three things: `schema_version == 1`, at most `MAX_WORKSPACE_ENTRIES` entries, and unique paths across the patch. It does **not** call `validate_portable_workspace_path`, does not check `base_manifest_digest` against any base, and does not bound per-file `size_bytes`. Those arrive later.

`apply_to(&self, base: &WorkspaceManifest)` (`lib.rs:784-825`) is the whole mechanism, and it is deliberately thin:

1. `self.validate()`.
2. Build a `BTreeMap<String, WorkspaceEntry>` from the base entries.
3. Apply each operation in listed order: `Remove` is `tree.remove(path)` — exact path only, no recursive delete, and an absent path is a silent no-op; `Directory` and `File` are `insert`, which **overwrites** any existing entry at that path, so a `File` → `Directory` type change at one path is expressible.
4. Collect `tree.into_values()` (already sorted by path) into a `WorkspaceManifest { schema_version: 1, .. }`.
5. `final_manifest.validate()?` and return.

The doc comment is explicit that this is the point: *"No second path validator is introduced: portable path, case-collision, parent-directory, symlink, depth, count, and size rules all come from `WorkspaceManifest::validate`."* Order independence follows from the uniqueness check in step 1 plus the fact that every operation touches a distinct path. The base lookup and digest match are the caller's job — the server does a principal-scoped `(principal_id, base_manifest_digest)` lookup before calling `apply_to` at `crates/eggwork-server/src/workspace.rs:318-323`.

Two failure modes are worth expecting, and both are covered by tests: a patch that adds a file under a nonexistent directory fails in step 5, and a patch that removes a directory while children remain also fails in step 5 (orphaned children hit the parent-closure rule). Both surface as the generic `InvalidPath { field: "workspace parent directory" }` rather than a patch-specific error.

### Relation to content addressing

The workspace model is the concrete form of ADR-0004: control objects carry digests and metadata, never file bodies (decision 3), and file bytes are addressed by `BlobDigest` with SHA-256 as the required initial algorithm (decision 2). A manifest is a *bounded portable description*, not a Git repository (decision 9) and not a path on a host (decision 6). `WorkspaceManifest::digest` is what lets a client ask which content the node is missing before upload, and what makes a patch self-describing: `base_manifest_digest` is a content address, so an unbound or wrong base is detectable by the caller before any apply.

## Outcome and event model

The three-way distinction is the heart of this section, and it is drawn from `plans/001-terminology-and-domain-model.md` §23-24.

**Rejection — never admitted.** `ExecutionRejection` (`lib.rs:890-899`) has seven variants: `Busy`, `Draining`, `CapabilityMismatch`, `Unauthorized`, `InvalidRequest`, `Conflict`, `StorageExhausted`. It is a standalone enum with no `ExecutionId` and no `ExecutionGeneration`, because nothing was admitted and therefore no identity exists. No child process exists as a result, and no event stream is ever opened. The domain model lists rejection examples including "impossible resource requirement, invalid workspace, or digest mismatch"; note that the enum has no dedicated variant for those three — they must land in `InvalidRequest` or `CapabilityMismatch`, so the enum is a coarser vocabulary than the prose. Per the terminology doc §24, rejection classification is not a process failure and must never be rendered as one.

**Failure — admitted, could not complete.** `ExecutionFailure` (`lib.rs:900-909`) has seven variants: `Spawn`, `Internal`, `OutputLimit`, `Sandbox`, `ResourceLimit`, `Interrupted`, `LeaseExpired`. It exists in exactly one place in the data model: `ExecutionResult.failure: Option<ExecutionFailure>`. So a failure is not a state — it is a typed fact that accompanies a state. Per §24, failure classifications are retry-neutral; the caller owns retry policy.

**Result — completed, with an exit status.** `ExecutionResult` (`lib.rs:936-954`): `state: ExecutionState`, `exit_code: Option<i32>`, `failure: Option<ExecutionFailure>`, `stdout_bytes`, `stderr_bytes`, `stdout_omitted`, `stderr_omitted` (all `u64`), `cleanup_warning: Option<String>`, and four `#[serde(default)]` fields: `finalization_failure: Option<ExecutionFinalizationFailure>`, `artifact_count: u32`, `sandbox: Option<SandboxResult>`, `resources: Option<ResourceResult>`. The `#[serde(default)]` markers on exactly those four make an older terminal record deserializable into the newer struct, which is the crate's only wire-evolution mechanism. The retained/omitted byte pair distinguishes "produced nothing" from "produced more than the capture budget kept", which is the observable consequence of `OverflowPolicy`.

Three separate post-execution channels are worth separating: `cleanup_warning` (free text, the soft signal), `finalization_failure` (typed, the hard signal), and `artifact_count` (a `u32` with **no** inline artifact list — the bodies and even the metadata are fetched separately, matching ADR-0004 decision 3 and `plans/001-terminology-and-domain-model.md` §13).

`ExecutionFinalizationFailure { ArtifactCapture, Retention }` (`lib.rs:931-935`) covers the case where the process finished but bookkeeping after it did not. Note it sits *inside* a result whose `state` is already terminal, and `cleanup_warning` can be set alongside it — consistent with ADR-0003's "cleanup diagnostics may be appended without changing the chosen terminal outcome".

**States.** `ExecutionState` (`lib.rs:878-889`) is a flat nine-variant enum: `Accepted`, `Preparing`, `Running`, `Cancelling`, `Succeeded`, `Failed`, `Cancelled`, `TimedOut`, `Interrupted`. There is no `is_terminal()` helper and no terminal-state grouping in this crate — the five terminal variants are a convention that the server applies. `Interrupted` is the conservative post-restart classification that per §27 must not imply safe automatic retry.

### `SandboxResult` and `ResourceResult`

`SandboxResult` (`lib.rs:910-917`) is internally tagged with `status` and snake_case: `NotRequested`, `NotApplied { reason: String }`, `Applied { profile: String }`, `Failed { reason: String }`. The `Applied` / `NotApplied` split is the typed answer to the terminology prohibition in §30 ("sandboxed" when only best-effort process limits were applied), and `profile` names which profile was actually in force.

`ResourceResult` (`lib.rs:925-930`) mirrors `ResourceRequirements` field for field — `memory_bytes`, `cpu_millis`, `pids` — each a `ResourceDimensionResult` (`lib.rs:918-924`): `NotRequested`, `NotApplied { reason }`, `Applied { backend }`, `LimitExceeded { backend }`. `LimitExceeded` is the runtime-hit case and has no request-side counterpart. Two asymmetries are visible in the source: the payloads differ (`reason` for `NotApplied`, a name for `Applied`/`LimitExceeded`), and neither variant records *what limit was actually applied* — only which backend enforced it. Also note `ResourceDimensionResult` carries **no** serde tag attribute, so unlike `SandboxResult` it serializes in externally tagged PascalCase.

`ResourceDimension { Memory, Cpu, Pids }` (`lib.rs:437-443`, `rename_all = "snake_case"`) is a fourth, separate naming of the same three dimensions. It is declared at `lib.rs:439` and never referenced anywhere else in the crate — it exists as a key-shaped vocabulary for dimension-addressed reporting that core itself does not use.

### Artifacts

`ArtifactRecord` (`lib.rs:956-968`) is the declared-output record: `artifact_id: ArtifactId`, `execution_id: ExecutionId`, `generation: ExecutionGeneration`, `path: RelativePath`, `kind: ArtifactType`, `digest: BlobDigest`, `size_bytes: u64`, `executable: bool`, `created_unix_ms`, `expires_unix_ms`. Note that an artifact *is* generation-scoped, unlike an event — it carries `ExecutionGeneration` explicitly, so a stale generation's artifacts are identifiable after a handoff. `ArtifactType` (`lib.rs:970-974`) is a single-variant enum with exactly one member, `File`, which is how the "declared outputs, not recursive dumps" boundary is expressed in the type system. There is no `validate()` on `ArtifactRecord`: nothing in core checks that `expires_unix_ms > created_unix_ms`.

### Events

`EventMetadata { fields: Vec<(String, String)> }` (`lib.rs:975-1006`). `validate` bounds the pair count by `MAX_METADATA_COUNT` and each key/value by `MAX_METADATA_KEY_BYTES` / `MAX_METADATA_VALUE_BYTES`. Two deliberate-looking differences from `ExecutionSpec::validate`: it does **not** require keys to be non-empty, and it does **not** reject NUL bytes. `Debug` prints only `field_count` and `"[REDACTED]"`.

`ExecutionEventKind { State(ExecutionState), Stdout(Vec<u8>), Stderr(Vec<u8>), Diagnostic(String) }` (`lib.rs:1007-1035`) — the four observation shapes. `ExecutionEvent { sequence: EventSequence, kind, metadata }` (`lib.rs:1036-1058`) and its `validate` bounds the single payload (stdout chunk, stderr chunk, or diagnostic) at `MAX_EVENT_CHUNK_BYTES` with `TooLong { field: "event payload" }`, and delegates metadata to `EventMetadata::validate`. `State` events are counted as zero payload and are therefore never chunk-rejected. The `Debug` impl redacts all three payload variants by printing length only.

Two things a reviewer should hold onto. The chunk bound is **per event**; the cumulative output bound is `OutputPolicy::capture_limit_bytes` / `MAX_CAPTURE_BYTES`, enforced by the runner that produces the events. And `ExecutionEvent` carries neither an `ExecutionId` nor an `ExecutionGeneration` — ADR-0003 requires generation-scoped sequencing, so the pairing must be established by the stream envelope outside this crate.

## Node capability and status

`NodeCapabilities { protocol: ProtocolVersionRange, features: Vec<String>, max_active_executions: u32 }` (`lib.rs:1060-1088`). Per §16, a capability is a *fact* about what an implementation can support or enforce — not current capacity. `validate` requires `protocol.min <= protocol.max` (using the derived `Ord` on `ProtocolVersion`, major first), at most `MAX_CAPABILITIES` features, and each feature non-empty, at most `MAX_METADATA_VALUE_BYTES`, and NUL-free. `max_active_executions` is not validated; `0` is a legal value meaning "admits nothing".

`NodeStatus { node_id, draining: bool, active_executions: u32, capabilities: NodeCapabilities }` (`lib.rs:1089-1095`) is the dynamic counterpart per §17, and it has **no `validate()` at all**. It embeds a full `NodeCapabilities` rather than referencing it, so a status read is self-contained for placement decisions — but nothing in core compares `active_executions` against `capabilities.max_active_executions`, and nothing in core decides anything on the basis of `draining`. Per §16-18, capability is not capacity and status is not a scheduling decision; placement belongs to the controller.

The relationship to the request model is the three-state correspondence, and core only supplies the vocabulary for it:

| Request asks | Requires a node capability | Outcome reported as |
|---|---|---|
| `IsolationRequirement::Required` | an isolation backend feature | `SandboxResult::Applied { profile }` |
| `IsolationRequirement::BestEffort` | (degradable) | `SandboxResult::NotApplied { reason }` |
| `ResourceRequirements` field `Requirement::Required(_)` | a resource backend feature | `ResourceDimensionResult::Applied { backend }` |
| `ResourceRequirements` field `Requirement::BestEffort(_)` | (degradable) | `ResourceDimensionResult::NotApplied { reason }` |
| `Requirement::NotRequested` | nothing | `ResourceDimensionResult::NotRequested` |
| `NetworkRequirement::Disabled` / `AllowListed(..)` | a network-control feature | *(no network outcome field exists in `ExecutionResult`)* |

Two asymmetries stand out. `NetworkRequirement` is the only one of the three requirement types with no outcome-side counterpart in `ExecutionResult` — the server can see `resources` and `sandbox` results but has nowhere to record what network policy was actually applied. And `SandboxResult` records what was applied, not what was asked for, so a `BestEffort` request that got `Applied` is indistinguishable in the record from a `Required` one.

The matching itself is **not** in this crate: `features` is a `Vec<String>` of opaque strings, and there is no registry of legal feature names, no matching function, and no rejection helper. `eggwork-server` does the comparison and emits a `capability_mismatch` response — visible at `crates/eggwork-server/src/lib.rs:1596-1601`, right before the digest computation.

## Canonical digests

Three digests, three domain-separation prefixes, three version axes.

### `request_digest(spec) -> BlobDigest`

`lib.rs:1155-1161`, paired with `CANONICAL_REQUEST_VERSION: u16 = 2` at `lib.rs:1150-1151` ("Version of the execution request canonicalization algorithm").

1. `normalize_execution_spec(spec)` (`lib.rs:1187-1203`) clones the spec and sorts the three semantically unordered collections: `command.environment` by `name`; `metadata` by `(key, value)`; `command.declared_outputs` by `(path, required)`. `argv` is deliberately left in order, because argv order is semantic. All three sorts use `sort_by`, which is stable.
2. Bytes are built as `b"eggwork-execution-spec\0canonical-json-v2\0"` followed by `serde_json::to_vec(&normalized)`.
3. `BlobDigest::from_bytes` SHA-256s the whole thing into lowercase hex.

**What is included:** the entire normalized `ExecutionSpec`, which means both `schema_version` values, all of `argv` in order, `cwd` (as JSON `null` when absent), every environment name *and value*, the full `stdin` payload, `timeout_millis`, the whole `output` policy, every `declared_output` path and flag, all resource requirements, `isolation`, `network`, and all metadata pairs. Nothing is excluded. In particular, secrets are *not* excluded from the digest input — the `Debug` redaction is a logging-layer property, and the canonical bytes transiently contain plaintext argv, environment values, and stdin.

**Why ordering is stable:** the hashed structure contains no serde map. Every type in it is a struct (serde writes fields in declaration order), an enum, or a `Vec`/`Option`. The only order-insensitive collections are the three that `normalize_execution_spec` sorts. `RelativePath` and the `id_type!` types serialize as plain JSON strings via `into = "String"`, and `Requirement<T>` serializes through its hand-written impl, so neither can introduce nondeterminism. This is the mechanism behind the claim in `architecture/domain.md` that canonical digesting "is independent of JSON map ordering because core request fields are ordered structs".

**What it is used for:** execution identity and idempotency. Per ADR-0003 decisions 2-4, submission identity is conceptually `(ExecutionId, ExecutionGeneration, RequestDigest)`; same id and generation with the same digest returns the existing accepted execution without spawning again, and the same id and generation with a *different* digest is an identity conflict. The server computes it and persists the pair at `crates/eggwork-server/src/lib.rs:1605-1616`.

Note that `request_digest` does **not** call `validate()`. It is a pure function of the spec's serialized shape, so an invalid spec (duplicate environment names, zero timeout, 300 args) is still digestible. Validation and canonicalization are independent steps and both are the caller's responsibility to run.

### `request_digest_with_workspace(spec, Option<&WorkspaceId>) -> (u16, BlobDigest)`

`lib.rs:1163-1185`, paired with `CANONICAL_WORKSPACE_REQUEST_VERSION: u16 = 3` at `lib.rs:1152-1153` ("Version used when a fixed workspace identity participates in execution identity").

- `None` → delegates to `request_digest` and returns `(CANONICAL_REQUEST_VERSION, digest)`. No second hashing pass.
- `Some(id)` → normalizes again, wraps the spec in a private `CanonicalWorkspaceRequest<'a> { spec, workspace_id }` with that exact field order, prefixes `b"eggwork-execution-spec\0canonical-json-v3\0"`, and returns `(CANONICAL_WORKSPACE_REQUEST_VERSION, digest)`.

The returned tuple exists so the *algorithm version* is stored alongside the digest; the workspace/no-workspace distinction is therefore a fact about stored identity records, not something a consumer has to infer from the digest bytes.

### What changes between version 2 and version 3

Three things, and only three:

1. **The domain-separation tag.** `canonical-json-v2` → `canonical-json-v3`, inside an otherwise identical `eggwork-execution-spec\0...\0` prefix.
2. **The JSON envelope shape.** Version 2 hashes the bare normalized spec object; version 3 hashes a two-field object `{ "spec": ..., "workspace_id": ... }`. Field order in the wrapper is fixed at declaration.
3. **The reported version integer.** `2` → `3`, returned to the caller for storage.

What does *not* change: the normalization function, the set of included fields, the hash, and the lowercase-hex encoding. Because the prefix differs, a version 3 digest can never collide with a version 2 digest for the same spec — the two identities live in disjoint domains, which is what allows both to coexist in one store. The recorded design intent is in `plans/closure/workspace-artifact-transport/002-status.md`: "Canonical requests without a workspace remain version 2. A workspace reference uses domain-separated canonical version 3 and participates in the request digest."

What version 3 does **not** bind: the workspace *manifest* content, the manifest digest, the principal, the node, the `ExecutionId`, the generation, or the lease. Only the `WorkspaceId` string participates, so whether two different manifests share an identity is decided upstream by the workspace service, not by this crate. Execution identity is therefore caller- and placement-agnostic by construction.

### `WorkspaceManifest::digest() -> BlobDigest`

Covered above: prefix `b"eggwork-workspace-manifest\0canonical-json-v1\0"`, entries sorted by path, and a *separate* version namespace from the request digests. This one is the content address for a tree (ADR-0004 decision 2) and doubles as the patch's `base_manifest_digest`.

### The synchronization hazard

The two version constants and the two prefix literals are **independent**. `CANONICAL_REQUEST_VERSION = 2` and the string `canonical-json-v2` do not reference each other; neither does `CANONICAL_WORKSPACE_REQUEST_VERSION = 3` and `canonical-json-v3`. Bumping a constant alone would leave the hashed prefix unchanged — the returned version would claim a new algorithm while the bytes still hash under the old domain separator — and no test pins the two together. This is the single most fragile thing in the crate.

## Error model

Two error shapes with a deliberate boundary between them.

### `ValidationError`

`lib.rs:31-47`, deriving `Debug`, `Clone`, `PartialEq`, `Eq`, and `thiserror::Error`. Seven variants, each carrying a `field: &'static str` and, where relevant, the `max` that was exceeded:

| Variant | Message | Typical source |
|---|---|---|
| `Empty { field }` | `{field} must not be empty` | `id_type!::new`, empty `argv` |
| `TooLong { field, max }` | `{field} exceeds its {max}-byte limit` | id length, env value, oversized argv entry (reported as `OutOfRange`), oversized event payload |
| `InvalidSyntax { field }` | `{field} has invalid syntax` | id charset, `BlobDigest::parse`, env name, duplicate env name, workspace case/duplicate path |
| `TooMany { field, max }` | `{field} exceeds its {max}-item limit` | argv, env, metadata, outputs, workspace entries, capabilities |
| `Forbidden { field }` | `{field} contains a forbidden value` | NUL in an env value, any workspace symlink |
| `InvalidPath { field }` | `{field} must be relative and confined` | `RelativePath::new`, portable workspace path, reserved device name, missing parent directory |
| `OutOfRange { field }` | `{field} is outside its supported range` | generation `0`, timeout `0`/oversized, `OutputPolicy`, `ResourceRequirements`, capability protocol range, metadata entry |

Three properties make this shape work. `field` is `&'static str`, so error text can never embed caller-supplied data — a validation error is not a secret-leak vector, and the labels are greppable. `max` is carried in the payload, so a caller can report the bound without re-deriving which constant applied. And `ValidationError` is **not** `Serialize` — it cannot be placed directly into a wire response, which forces an explicit mapping at the boundary.

Its limitation: `field` is a human-chosen label, and the labels are not consistently field names. Some are real fields (`"argv"`, `"environment"`, `"timeout"`, `"stdin"`, `"metadata"`, `"captabilities"`); others are synthetic descriptions (`"argv entry"`, `"environment value NUL"`, `"duplicate environment name"`, `"workspace case collision"`, `"duplicate workspace path"`, `"reserved workspace path"`, `"sha256 blob digest"`, `"execution generation"`, `"resource requirements"`, `"capability"`, `"protocol version range"`). A consumer that parses `field` to identify the offending struct field cannot rely on it.

Where it is produced: the five constructors (`id_type!::new`, `ExecutionGeneration::new`, `BlobDigest::parse`, `RelativePath::new`, `EnvironmentEntry::new`), the private `validate_portable_workspace_path`, and the `validate` methods on `StdinPolicy`, `OutputPolicy`, `ResourceRequirements`, `CommandSpec`, `ExecutionSpec`, `WorkspaceManifest`, `WorkspaceManifestPatch`, `EventMetadata`, `ExecutionEvent`, `NodeCapabilities`. Every one of those is deterministic and side-effect-free; the entire error vocabulary is producible with no I/O.

### `ApiError`

`lib.rs:1143-1148`: `{ schema_version: u16, code: String, message: String }`. A control-plane response envelope with **no** code enum, no details field, no retryability hint, and no linkage to `ExecutionRejection` or `ValidationError`. The code vocabulary is a server-owned string convention — observed codes include `capability_mismatch` (409), `invalid_request` (400), and `workspace_not_ready` (409) at `crates/eggwork-server/src/lib.rs:1596-1631`. Nothing in core can detect a typo'd or unmapped code, and adding a rejection variant does not force a corresponding `ApiError` code to exist.

### Why the split matters

`ValidationError` answers "is this domain value well-formed within its bounds?" and is a pure, exhaustive, statically-typed vocabulary produced entirely inside core. `ApiError` answers "what did the node return to this client?" and is a presentation/transport shape whose vocabulary is decided by the server. Keeping them separate means core can be complete and exhaustive about *bounds* without committing to a wire contract it deliberately does not own, and it means a transport change (new code strings, new status mapping, richer details) requires no change to the domain crate. The cost is a hand-written mapping at one place, and the risk that the two vocabularies drift — which is a real review concern, not a theoretical one.

| Serde round-trip fidelity of a full `ExecutionSpec` | `#[serde(try_from/into)]` + derives | `paths_env_metadata_outputs_and_roundtrip` (one round-trip equality assertion) |

## Dependencies

Six external crates, all inherited from `[workspace.dependencies]` via `.workspace = true` in `crates/eggwork-core/Cargo.toml`:

| Crate | Why it is required |
|---|---|
| `serde` (derive) | `Serialize`/`Deserialize` on nearly every type, and the *derive machinery* for the six id types, `RelativePath`, and `BlobDigest` via `try_from`/`into`. Without derive, the domain types could not cross a process boundary at all. |
| `serde_json` | (a) `Requirement<T>`'s hand-written `Deserialize` buffers through `serde_json::Value` to distinguish `null` / bare / `{"required":…}` (`lib.rs:389`) — this is a *semantic* need, not a convenience. (b) Both canonical digest functions serialize with `serde_json::to_vec` and return `Result<_, serde_json::Error>`. (c) `WorkspaceManifest::digest` likewise. |
| `thiserror` | `ValidationError` is 7 variants of struct-shaped payloads with formatted messages; the derive removes the `Display` boilerplate that the error vocabulary would otherwise dominate. |
| `sha2` | `Sha256::digest` in `BlobDigest::from_bytes` — the crate's entire content-addressing authority. |
| `hex` | `hex::encode` for the lowercase hex digest representation, which is the canonical textual form `BlobDigest::parse` then enforces. |

There is **no** async runtime, no HTTP/TLS stack, no database, no filesystem, no serialization format other than JSON, and no logging framework. `std` supplies only `fmt`, `time::Duration`, and `collections::{HashSet, BTreeMap, BTreeSet}`.

**No workspace-internal dependencies, and that is machine-checked.** `crates/eggwork-core/Cargo.toml` lists only the six externals, and `scripts/check_execution_ownership.py::check_dependencies` (`scripts/check_execution_ownership.py:171-203`) parses `cargo metadata` and fails if `eggwork-core` depends on `eggwork-runner`, `eggwork-server`, or `eggwork-client`. That script runs in the CI `rust` job, alongside a `--prove-negative-exit` self-test that proves the guard actually fails on a forbidden pattern. The same script's process-ownership scanner additionally forbids `eggwork-core` from creating OS children, matching `architecture/execution-ownership.md`.

One honest caveat about that guarantee: the guard forbids three *named* crates. It does not assert that the dependency set is empty, so a new fourth workspace crate (for example `eggwork-sandbox-helper`) would not be caught. `#![forbid(unsafe_code)]` at `lib.rs:1` is stricter than the workspace's `unsafe_code = "deny"` lint, and `Cargo.toml` opts into `[lints] workspace = true`. The crate also uses edition-2024 let-chains (`lib.rs:289-291`, `lib.rs:393-396`) against the workspace `rust-version = "1.89"`, so the language-version floor is load-bearing for this file.

## Test coverage

`mod tests` is `lib.rs:1205-1671`: fifteen `#[test]` functions plus four fixture helpers (`spec`, `patch_base_manifest`, `patch_for`, and two local closures). There is no `#[test]` for `validate` behavior in a separate integration-test file — the entire suite is in-crate and uses `use super::*`.

What is genuinely well covered:

- **Identity and digest primitives** — `typed_ids_and_digest_validate`: `NodeId::new("node_1")` accepted, `"../bad"` rejected, `ExecutionGeneration::new(0)` rejected, generation ordering `1 < 2`, the exact SHA-256 of `b"abc"` (`ba7816bf…15ad`) as a known-answer test, and `BlobDigest::parse("ABC")` rejected for uppercase.
- **Spec validation and bounds** — `spec_and_bounds_validate`: a baseline spec validates; a cleared `argv` and an oversized `argv[0]` are both rejected.
- **Path and environment safety** — `paths_env_metadata_outputs_and_roundtrip`: `/tmp` and `a/../b` rejected, `1BAD` env name and NUL-bearing env value rejected, plus a `serde_json` to-string/from-string equality round trip of a full `ExecutionSpec` — the only round-trip assertion in the crate.
- **Secret redaction** — `execution_spec_debug_redacts_credentials_and_command_arguments` is the most security-relevant test: it plants four distinct secrets (in argv, env, stdin, and spec metadata), asserts none appear in the `Debug` output, asserts `[REDACTED]` is present, and repeats the check for an `ExecutionEvent` carrying both a stdout payload and event metadata.
- **Capability bounds** — `capability_bounds_validate`: a well-formed range validates; inverting `min`/`max` fails.
- **The `Requirement<T>` serde contract** — `resource_requirements_preserve_legacy_best_effort_shape_and_accept_required_values` is thorough: it checks all three deserialization shapes, both serialization shapes, the full `ResourceRequirements` JSON with `null` fields, a valid mixed case, and a `Required(0)` rejection.
- **Request digest normalization** — `canonical_request_digest_ignores_unordered_field_order`: reversing environment and metadata order yields an identical digest, and changing `argv[1]` changes it. `workspace_identity_participates_in_versioned_execution_digest` pins the version tuple (`3` with a workspace, `2` without) and digest distinctness.
- **Workspace tree validation** — three tests cover the portable-path rules and reserved names, file/directory conflict, exact duplicate, case collision, missing parent, symlink rejection, depth, entry count, and logical size, plus order-independent manifest digest and `logical_bytes`.
- **Workspace patches** — three tests cover schema/count/uniqueness, order independence, and digest equivalence against the equivalent full manifest, plus the five cases where a patch would produce a tree the full validator rejects and the absent-path-remove no-op.

Where coverage is thin, honestly:

- **Every stream and time bound is untested.** `StdinPolicy::validate`, `OutputPolicy::validate`, the `MAX_TIMEOUT` ceiling and the zero-timeout rejection, and `ExecutionEvent::validate`'s `MAX_EVENT_CHUNK_BYTES` check have no test at all. `MAX_EVENT_CHUNK_BYTES` and `MAX_ENV_VALUE_BYTES` are imported by `eggwork-runner`, so this crate is not the only place those numbers are enforced — but nothing pins the two implementations together.
- **`ExecutionSpec::validate`'s own checks are untested**: `schema_version == 0`, metadata count, key/value lengths, and NUL bytes. Only the nested `command.validate()` is exercised, via the valid-baseline test.
- **`EventMetadata::validate` and the `NodeCapabilities` feature bounds** are untested beyond the protocol range; count, length, and NUL rejections are not.
- **No boundary-value tests.** Every limit is tested either well inside it (if at all) or not at all. No test asserts "exactly `MAX_X` is accepted" or "`MAX_X + 1` is rejected", except the workspace count/depth/size tests, which do test `MAX + 1`.
- **No outcome or envelope types are tested.** `ExecutionState`, `ExecutionRejection`, `ExecutionFailure`, `SandboxResult`, `ResourceResult`, `ExecutionFinalizationFailure`, `ExecutionResult`, `ArtifactRecord`, `ArtifactType`, `ExecutionAccepted`, `ExecutionSnapshot`, `ApiError`, `NodeStatus`, `Versioned<T>`, and `ResourceDimension` appear in no test — so their serde shapes, including `SandboxResult`'s internal `status` tag and `Requirement`'s `#[serde(default)]` back-compat behavior on `ExecutionResult`, are unpinned.
- **Only `NodeId` is exercised** out of six id types, and the same for `WorkspaceId` and `ArtifactId` used inside tests. They share one macro, so this is lower risk than it looks.
- **`ExecutionHandle`'s lease redaction is untested** even though the same test file proves redaction for four other types — a regression there would not be caught.
- **No test pins the digest prefix strings to the version constants**, and none covers `declared_outputs` ordering even though the normalizer sorts it.
- **No negative test for `request_digest` on an invalid spec.** Because the digest functions do not validate, it is not established in the suite that this is intentional.

## Review focus

- **Prefix/constant desynchronization is the top risk.** The literals `canonical-json-v2` (`lib.rs:1158`) and `canonical-json-v3` (`lib.rs:1176`) are independent of `CANONICAL_REQUEST_VERSION` and `CANONICAL_WORKSPACE_REQUEST_VERSION` (`lib.rs:1151`, `lib.rs:1153`). Bumping a constant without editing the literal would report a new algorithm version while hashing under the old domain separator, and no test fails. A reviewer should require that the two are derived from one another, or add a test that asserts the literal matches the constant.
- **`ExecutionGeneration` can be constructed as `0` through serde.** `#[serde(transparent)]` over `u64` with the zero-check only in `new` means any stored or foreign record containing `0` deserializes into an invalid fencing token for a primitive whose entire purpose is to fence stale owners. `EventSequence` deliberately permits `0`, so the asymmetry is likely intentional — but the bypass on `ExecutionGeneration` should be closed or explicitly accepted. Both need a test.
- **Redaction is a `Debug`-only property and the digest sees plaintext.** `Debug` hides argv, environment values, stdin, event payloads, event metadata, and `ExecutionHandle::lease_id`, but `Serialize` is derived and unredacted throughout, and both digest functions hash plaintext argv, environment values, stdin, and metadata. `ExecutionHandle` serializes a bearer-authority token with no redacting wrapper. Per `plans/001-terminology-and-domain-model.md` §6, secrets should be stable references or excluded; a reviewer should confirm that nothing in the logging path serializes these types instead of formatting them.
- **Public fields make validation opt-in.** Nearly every type here is `pub` fields plus a `validate()` that must be called, and several types have no validator at all: `ExecuteRequest`, `ExecutionAccepted`, `ExecutionSnapshot`, `NodeStatus`, `ArtifactRecord`, `ExecutionResult`, `Versioned<T>`, and both `IsolationRequirement` and `NetworkRequirement` (which have no data to validate but also no enforcement that `NetworkRequirement::AllowListed` is bounded — its `Vec<String>` has no count or length limit anywhere). `WorkspaceManifest::digest()` does not validate before hashing. Contrast `eggwork-runner`'s `RunnerRequest`, which makes validated fields private so callers *cannot* bypass bounds (`architecture/overview.md:53`); a reviewer should decide whether core needs the same structural guarantee or whether validator coverage is sufficient.
- **Bounds that are not constants.** The resource ceilings `1_125_899_906_842_624`, `1_000_000`, and `1_000_000` (`lib.rs:412-425`) and the `OutputPolicy::default()` values 1 MiB / 16 KiB (`lib.rs:316-317`) are inline literals. Every other bound in the crate is a discoverable `pub const`, so a caller cannot pre-flight these. Also note `MAX_METADATA_VALUE_BYTES` is doing double duty as the `NodeCapabilities.features` length bound (`lib.rs:1080`), so raising event-metadata value capacity would silently raise feature-name capacity too.
- **Inconsistent serde representation across the same crate.** Internally tagged snake_case: `WorkspaceEntry`, `WorkspacePatchEntry` (`type` tag) and `SandboxResult` (`status` tag). Externally tagged PascalCase: `ExecutionState`, `ExecutionFailure`, `ExecutionRejection`, `ExecutionFinalizationFailure`, `ResourceDimensionResult`, `ExecutionEventKind`, `StdinPolicy`, `OverflowPolicy`, `IsolationRequirement`, `NetworkRequirement`. Two neighboring result types disagree. A later wire freeze must encode all of these, and `Requirement<T>`'s `serde_json::Value`-based `Deserialize` additionally makes that type unusable under any non-JSON codec.
- **Digest input blind spots.** Normalization sorts but never dedupes, and no validator rejects duplicate `declared_outputs` paths (unlike duplicate environment names), so two specs differing only in duplicated declared outputs hash differently while describing the same capture set. The digest also binds neither the workspace manifest content nor the principal, so execution identity is caller-agnostic by construction and two materially different trees under one `WorkspaceId` produce one identity.
- **Workspace patch validation is deferred and partial.** `WorkspaceManifestPatch::validate` checks schema, count, and unique paths only — not `validate_portable_workspace_path`, not per-file `size_bytes`, and not that `base_manifest_digest` matches any base (the server does the principal-scoped lookup). Portable-path and tree-coherence failures therefore surface from `apply_to` as generic `InvalidPath`/`OutOfRange` errors with no indication which patch operation caused them. Removing a directory while children remain is a correct rejection but an unhelpful message.
- **Unvalidated cross-field coherence in the outcome types.** `ExecutionResult` has no `validate()`, so nothing prevents `state: Succeeded` with `failure: Some(..)`, a `Failed` state with no failure, or a terminal state with no `exit_code`; ADR-0003's "terminal state is single-assignment" is entirely the server's invariant. `Interrupted` exists in *both* `ExecutionState` and `ExecutionFailure`, so `state: Interrupted, failure: Some(Interrupted)` and `state: Failed, failure: Some(Interrupted)` are both representable and core does not say which is authoritative. `NodeStatus.active_executions` is never compared to `NodeCapabilities.max_active_executions`, and `ArtifactRecord.expires_unix_ms` is never checked against `created_unix_ms`.
- **Declared-but-unused and asymmetric surface.** `ResourceDimension` and `Versioned<T>` are defined and never referenced anywhere in the crate. `BlobDigest` lacks `Ord` while nearly every other bounded type has it. `NetworkRequirement` has no outcome-side counterpart in `ExecutionResult` (unlike resources and sandbox). `ResourceResult` records which backend applied a limit but never *what limit*. `ExecutionEvent` carries no `ExecutionGeneration` and no `ExecutionId`, so ADR-0003's generation-scoped sequencing must be established entirely by the stream envelope outside this crate. `SandboxResult` records what was applied, not what was requested, so a `BestEffort` isolation request that was fully applied is indistinguishable from a `Required` one.
- **Test depth is concentrated where it is least likely to break.** The fifteen tests are thorough on identity, redaction, `Requirement` serde, and workspace trees, and empty on every stream/time bound, `ExecutionSpec`'s own metadata rules, all outcome and envelope serde shapes, boundary values, and the digest prefix/version coupling. The `MAX_*` numbers a remote caller depends on are the least-tested part of the crate.
